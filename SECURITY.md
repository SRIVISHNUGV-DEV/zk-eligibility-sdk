# Security Guarantees & Threat Model

** This SDK intentionally does not attempt to solve identity,
sybil resistance alone, or social trust.
It proves on-chain facts only **

---

## Cryptographic Guarantees

If a proof generated by this SDK **verifies successfully**, we guarantee:

✅ **The statement is cryptographically true**
- Mathematical certainty, not probabilistic
- No way to forge or fake a valid proof

✅ **The proof uses industry-standard Groth16**
- BN128 elliptic curve
- Published verification keys
- Auditable constraint system

✅ **The prover could not have succeeded unless the statement was true**
- Soundness guarantee (Groth16 assumption)
- No backdoors or escapes

**These guarantees are absolute within stated assumptions.**

---

## What We Assume (Explicitly)

No ZK system is assumption-free. Ours are:

### 1. Correct Blockchain Data
**Assumption:** Your RPC provider (Alchemy, Infura, etc.) returns truthful, canonical chain data.

**Why it matters:** All eligibility statements depend on on-chain facts.

**Mitigation:**
- Use reputable, audited providers (Alchemy, Infura, QuickNode)
- Run your own node for maximum trust
- Verify consistency across multiple providers

**If violated:** Proofs reflect incorrect facts. Not the SDK's fault—provider's.

---

### 2. Trusted Setup Integrity
**Assumption:** The Groth16 trusted setup was performed correctly by trusted parties.

**Why it matters:** Groth16 requires a one-time setup. If compromised, soundness breaks.

**Mitigation:**
- We use standard Groth16 trusted setup procedures
- Verification keys are public and auditable
- Ceremony was multi-party (multiple organizations)

**Status:** ✅ Standard and secure

---

### 3. Honest prover
**Assumption:** The SDK generates witness data internally; users cannot inject arbitrary values.

**Why it matters:** Proofs are only sound if inputs are correct.

**How we protect this:**
- SDK fetches blockchain data directly
- Any modification to witness values that violates constraints will cause proof generation or verification to fail 
- All inputs are validated before ZK execution proving efficacy

**Status:** ✅ Enforced by design

---

### 4. Cryptographic Hardness
**Assumption:** Discrete logarithm problem is hard on BN128. Elliptic curve crypto is secure.

**Why it matters:** These are foundational to all ZK proofs.

**Mitigation:** These are the same assumptions used by Bitcoin, Ethereum, and all major ZK projects.

**Status:** ✅ Well-established, standard

## Threat Model

### Adversaries We Consider

👤 **Users attempting to fake eligibility**
- Trying to generate false proofs
- **Result:** Cryptographically impossible. Proof generation will fail.

👤 **Users trying to overflow circuits**
- Submitting `minTx = 2^256`
- **Result:** Caught at SDK level, rejected before ZK

👤 **Developers misusing the SDK**
- Using invalid parameters or wrong circuits
- **Result:** Clear error messages, safe defaults, documentation

---

### Adversaries We Do NOT Consider

❌ **Fully malicious RPC provider**
- If Alchemy is hacked, we cannot prove historical facts
- **Mitigation:** Use trusted providers or your own node

❌ **Consensus-breaking blockchain attack**
- 51% attack, finality violation, etc.
- **Mitigation:** This is blockchain's problem, not ours

❌ **Cryptographic breaks**
- If SHA-256 or elliptic curves break
- **Mitigation:** Same assumption as all of Web3

---

## What This SDK Does NOT Prove

### These Are Out of Scope

❌ **Wallet ownership** (no signature verification)  
❌ **Identity or humanity**  
❌ **Intent or motivation**  
❌ **That wallet is not a contract**  
❌ **That RPC provider is not adversarial**  
❌ **Real-time guarantees under chain reorgs**  
❌ **Off-chain business logic correctness**  

**This is intentional.** These are your application's responsibility , we explicitly state that checking these lie within your responsibility and not ours

## Parameter Validation & Overflow Safety

### Design Principle

> **All insane inputs are caught before any ZK computation.**

### What We Validate

✅ **Range checks**
- `minTx` cannot exceed chain's total transactions
- `cooldownBlocks` cannot exceed chain age
- Block numbers fit in 64 bits

✅ **Sanity checks**
- Negative values rejected
- Absurd values rejected
- Non-integer values rejected

✅ **Early failure**
- TypeScript validation runs first
- No cryptographic operations on bad data
- Deterministic error messages

### Example
```typescript
// This is caught BEFORE ZK execution:
const proof = await SDK.prove("MIN_ACTIVITY", wallet, {
  minTx: -100  // ❌ Rejected
});
// Error: INVALID_MIN_TX
// Result: Safe, no proof generated
```

## ZK Circuit Safety

### All Circuits

✅ Use explicit bit-widths (64-bit primary, 32-bit comparisons)  
✅ Contain no unconstrained signals  
✅ Enforce boolean outputs (0 or 1 only)  
✅ Fail cryptographically if constraints violated  

### No Circuit

❌ Defaults to true  
❌ Silently overflows  
❌ Auto-corrects invalid values  

**If a constraint fails, the proof fails. Period.**

## Failure Modes

The SDK fails in exactly three explicit ways:

### Type 1: Input Validation Failure (Fastest)
```
Invalid parameters → TypeScript error
No ZK computation
Deterministic failure message
Example: minTx > chain height
```

### Type 2: Cryptographic Failure
```
Constraint violation → Proof generation fails
Witness generation error
Deterministic failure
Example: first_tx > current_block
```

### Type 3: External Failure
```
RPC provider down → Network error
No proof generated
Clear error code
```

**All failures are:**
- ✅ Deterministic (same input = same failure)
- ✅ Explicit (clear error messages)
- ✅ Safe (no silent partial success)
- ✅ Non-ambiguous

## Side-Channel Considerations

### What We Do NOT Protect

⚠️ **Timing side-channels**
- Proof generation time varies by circuit complexity
- No effort made to hide timing

⚠️ **Memory access patterns**
- Standard implementation (not constant-time)

### Why This Is Okay

For most Web3 use cases (eligibility proving, airdrop gates), timing attacks are impractical:
- Users run SDK on their own machine
- No observable timing from untrusted observer
- Adversary cannot measure precise timing

### For High-Adversarial Environments

If you need side-channel resistance:
- Run proof generation on isolated hardware
- Or implement custom constant-time variants
- Not in scope for v1.0

## On-Chain Verification

### Proofs Are Fully Verifiable On-Chain

✅ Standard Groth16 format  
✅ No private data required  
✅ Can be verified by any Solidity smart contract  
✅ ~280k gas per verification (typical)  

### Example Solidity Verifier
```solidity
function verifyEligibility(
  uint256[2] calldata pi_a,
  uint256[2][2] calldata pi_b,
  uint256[2] calldata pi_c,
  uint256[4] calldata publicSignals
) external view returns (bool) {
  return verifier.verifyProof(pi_a, pi_b, pi_c, publicSignals);
}
```

## Versioning & Immutability

### v1.x Guarantees Are Locked

🔒 **Cannot change:**
- Circuit definitions
- Constraint systems
- Verification key
- Semantics of rules

✅ **CAN change:**
- Internal SDK implementation
- Error messages
- Documentation
- Non-breaking bug fixes

### Breaking Changes Require v2.0

**Why?** Once you've generated proofs under v1.0, they must verify forever under v1.0. No surprises.
